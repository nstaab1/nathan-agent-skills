Ticket 3 · fixing-flaky-tests

DecisionQ
A flaky test both failed and passed on the same commit. Failing every attempt is a real failure.7, 8
One shipped Node script, the verdict script, copied into each repo with a version line.27, 43, 44
It wraps the test command, so it sees the real exit code.42
It does the retry itself and compares two results files. It reruns only the failures when the repo has a command for that, and the whole command otherwise.69
No detection from manual reruns in the first version.70
One flaky-test record per test case, titled with classname plus name, labelled ready-for-agent.6, 30, 31, 36
Quarantine is a tracker label, with no change to test code.ADR 1
Into quarantine: three occurrences, in 30 days, across at least two branches, under a cap of 5% of the suite.8, 2, 3, 32
Out of quarantine: fix merged, or 30 days pass. A human is warned seven days before.32, 40
Tracker unreachable means nothing is treated as quarantined.33
Works with GitHub and GitLab trackers. Fork pull requests get a verdict but can't record.45, 46
The scheduled agent takes quarantined records first, opens at most three fix PRs per run with 20 passes in a row as proof, and never merges.6, 38
It may delete a flaky test only when the test is one of the five unneeded kinds.7
A fixed test that flakes again reopens its old record.39
The skill has its own setup step, delivered as a PR, and warns when scheduled agents aren't documented.49, 10
