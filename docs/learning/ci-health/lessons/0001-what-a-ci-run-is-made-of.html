What a CI run is made of

You described CI as "a list of jobs that fire to verify the code changes". That is right. This lesson adds the two layers under a job, and the one number that decides whether you get a green tick.

What you'll be able to do: look at any failed build and say which step failed and why the whole build went red. The verdict script in your design works entirely through this mechanism.

Four parts

PartWhat it is
RunOne execution of the pipeline for one commit.
JobA list of steps that go in order on one runner.
StepOne command, such as pytest.
RunnerA fresh machine for one job. It has a copy of your repo and nothing else, and it is thrown away afterwards.

These are GitHub's words for the parts. GitLab and others use slightly different names for the same shape. Source: Understanding GitHub Actions.

The exit code decides everything

When a command finishes it hands back a number called its exit code. CI reads only that number.

Exit codeCI's reading
0The step passed.
anything elseThe step failed.

CI does not read the test output or count failures. pytest exits with 1 when a test fails, and that 1 is the whole message. Source: Setting exit codes for actions.

Why this matters for your design

The verdict script is a command in the test job. It has one way to say "this build should fail": exit with a non-zero code. It has one way to say "let it through": exit with 0. Quarantine works because the script can see a failed test and still exit 0.

The second diagram also shows a trap. If the tests are their own step and they fail, a later step is skipped by default. A verdict script placed after them would never get a turn. That is the reason the design has the script wrap the test command, as you approved in Q42:

node verdict.mjs -- pytest --junitxml=results.xml

The script starts pytest itself, waits, looks at what happened, and then chooses the exit code for the step.
