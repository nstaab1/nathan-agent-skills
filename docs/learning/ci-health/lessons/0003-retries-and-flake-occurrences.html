Retries and flake occurrences

In lesson 2 you read a results file and said which tests passed and failed. One file is a single snapshot. A flaky test can't be seen in a single snapshot, because the definition needs two results.

What you'll be able to do: given the results of two attempts, sort every test into passed, real failure or flake occurrence. You'll also see why the verdict script does the retry itself instead of leaving it to the test framework.

What a flake occurrence is

The repo glossary says a flaky test is one that both failed and passed on the same commit with no code change. Google's testing team uses the same definition (Flaky Tests at Google). A flake occurrence is one CI run where that happened.

To see it you have to run the test again. That second go is a retry.

Where the retry comes from

Most frameworks can retry by themselves. With pytest --reruns 2 (from the pytest-rerunfailures plugin) or vitest --retry=2, the framework quietly reruns any test that fails. The obvious design would let the framework retry and have the verdict script read the fail-then-pass out of the JUnit XML file.

Why that isn't enough

That only works if the framework writes the retry into the file. Lesson 2 ended by warning that this is the part where tools differ.

ToolWhat the file shows for fail-then-passCan the script see the flake?
Maven, GradleA <flakyFailure> element inside the testcase (Surefire docs)Yes
pytest with the reruns pluginReported to look like an ordinary pass. A fix that adds flakyFailure is proposed, and its release status is unconfirmed (pull request 380)No
VitestOne project reports the file carries no retry information, and Vitest's docs don't say otherwise (their workaround)No

The pytest and Vitest rows rest on third-party reports, not on running the tools. Ticket #17 checks them against real files. If the reports are right, a flaky test that passes on a framework retry leaves a file identical to one where it passed first time, and the verdict script would record nothing.

So the verdict script retries

The verdict script already starts the test command itself (lesson 1), so it can also do the retry. It doesn't need the framework to describe the retry, because it ends up holding two ordinary files and compares them.

The cost is a second run whenever something fails. If the framework has a command that reruns only the failed tests, the repo records it in its CI doc and the script uses it. Otherwise the script reruns the whole test command. The framework's own automatic retries are switched off so the two don't overlap.
