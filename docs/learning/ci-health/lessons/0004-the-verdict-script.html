The verdict script

You now have every piece the verdict script uses: the exit code from lesson 1, the results file from lesson 2, and the two-attempt comparison from lesson 3. This lesson puts them in order.

What you'll be able to do: take any situation in a test job and say what the verdict script does: which exit code it gives, and whether it records anything.

Its two jobs

The repo glossary defines the verdict script as the script that runs a CI job's tests, retries the failures, records flake occurrences and decides whether the build passes, ignoring failures of quarantined tests. That is two outputs:

OutputWhere it goes
An exit codeTo CI, which turns it into a green tick or red cross.
Flake occurrencesTo the issue tracker, as a comment on that test's flaky-test record.

What it does, in order

The steps in words

1. Run the tests. The script starts the test command itself and keeps two things: the command's exit code and results file 1.

2. Check for failures. If file 1 has no failed test, the script looks at the command's own exit code. Zero means a clean run. Non-zero with no failed test means the test command crashed before it could report, so the build fails. This is the case || true would have hidden.

3. Run the failures again. If the repo's CI doc names a command that reruns only the failed tests, the script uses it. If not, it reruns the whole test command. Either way it gets results file 2.

If the rerun crashes, writes no readable results file, or leaves out a test that failed in attempt 1, the build fails. A missing result is never treated as a pass.

4. Compare, test by test. For each test that failed in attempt 1:

In attempt 2 it…So it is…The script…
passeda flake occurrencerecords it on the test's flaky-test record and adds a line to the run summary
failed, and is quarantineda known flaky testignores it
failed, and is not quarantineda real failurefails the build

5. Give the verdict. If nothing is left that must fail the build, exit 0.

Where the quarantine list comes from

In step 4 the script asks the issue tracker which tests carry the quarantine label. If the tracker can't be reached, the script treats the list as empty. An outage can therefore make a build stricter, and can never let a real failure through.

One consequence to be clear about: while a test is quarantined, the script can't tell "flaked twice" from "is truly broken now". Both are ignored. The 30-day expiry and the cap on quarantined tests exist to limit that blind spot. Lesson 5 covers them.
