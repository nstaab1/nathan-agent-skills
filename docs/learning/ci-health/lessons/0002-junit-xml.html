JUnit XML: the results file every framework can write

In lesson 1 you saw that CI reads one number from a step, the exit code. An exit code of 1 says "something failed". It doesn't say which test. The design needs to know which test, so it needs a second source of information.

What you'll be able to do: open a JUnit XML file and say which tests passed, failed or were skipped, and what name the design would track each one under.

The problem it solves

Every test framework prints results to the terminal in its own style. A script that had to read pytest's text, Vitest's text and Go's text would need a separate reader for each one.

Nearly every framework can also save its results to a file in one shared layout, called JUnit XML. The name comes from JUnit, a Java test tool whose report layout other tools copied. You don't need Java or JUnit to use it.

You turn it on with a flag. In pytest it is --junitxml=results.xml (pytest docs). In Vitest it is --reporter=junit (Vitest docs).

What the file looks like

It is three kinds of box, one inside the next.

Here is a real-shaped file from a pytest run of four tests:

<testsuites>
  <testsuite name="pytest" tests="4" failures="1" skipped="1">

    <testcase classname="tests.test_cart" name="test_add_item"/>

    <testcase classname="tests.test_cart" name="test_checkout_total">
      <failure message="assert 39 == 40"/>
    </testcase>

    <testcase classname="tests.test_cart" name="test_remove_item"/>

    <testcase classname="tests.test_tax" name="test_vat_rounding">
      <skipped message="not ready"/>
    </testcase>

  </testsuite>
</testsuites>

How to read one testcase

Look at what is inside the testcase.

Inside the testcaseMeaning
nothingThe test passed.
<failure>An assertion was wrong. The test ran and the answer was not what it expected.
<error>The test blew up before it could finish, for example an exception or a timeout.
<skipped>The test did not run.

So in the file above: test_add_item and test_remove_item passed, test_checkout_total failed, and test_vat_rounding was skipped.

The name the design tracks

Each testcase carries two labels: classname, which says where the test lives, and name, which is the test itself. In Q30 you approved using the two together, exactly as written in the file, as the test's identity. The flaky-test record for the failure above would be titled:

flaky: tests.test_cart test_checkout_total

Frameworks fill in classname differently. pytest writes a dotted module path like tests.test_cart. Vitest writes the file path, like tests/cart.test.ts. The verdict script doesn't care about the difference. It copies whatever is there, which is why no per-framework naming rules are needed.

One honest caveat

There is no official JUnit XML standard. It is a convention that tools agree on in practice, and each tool has small differences (test report formats). Everything in this lesson is in the part they all share. The part where they differ is how a retried test is written down, and that is lesson 3.
